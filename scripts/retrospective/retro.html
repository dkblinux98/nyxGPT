Acceptance-perspective classification. The 266 issues labeled Acceptance Failure (implementation defects found at stakeholder acceptance, before release) are classified by root cause: escaped defect — broken behavior in code that had passed review (a review miss); spec gap — the delivered work matched the issue but the requirement itself was wrong or incomplete (redesigns, consolidations, UX corrections); workflow miss — the agent pipeline itself failed (review gate, branch hygiene, submission workflows). Classification is keyword-heuristic over titles and bodies, hand-reviewed.

Product management failures. The 59 issues labeled Improvement are counted as a separate failure statistic: an Improvement filed during acceptance testing means the spec itself was incomplete — a product-management (planning) failure, distinct from an Acceptance Failure (implementation defect). Since 2026-08-12 (#3731) an Improvement gates a feature's move to release exactly as a failure does; the label separates the two as a statistic, not as a gate.

Failure-issue model (since 2026-08-02; storage changed 2026-08-12, #3731). A unique acceptance failure becomes a new issue labeled Acceptance Failure that blocks the original feature through GitHub's native blocked-by/blocks relationship — the only place the link is stored. The Related feature: #N body convention is retired, still read as a fallback for issues filed before that date. The original feature stays closed. A fix that later fails stakeholder re-test reopens the same failure issue rather than filing a new one — so failure-issue counts understate total failure rounds.

Sprints. Sprint buckets are the Project's real Sprint iterations, read from the snapshot committed by the "Retro Dashboard - Dump Project Fields" workflow (scripts/retrospective/data/project_fields.json) — each issue lands in the sprint it was actually assigned to on the board, and Module values come from the Project's Module field. If the snapshot is missing, the builder falls back to calendar weeks bucketed by creation date and title-inferred modules (the sprint-axis caption says which mode is active). The last-7-days section always uses title-inferred modules. Milestones are the repo's phase milestones, ordered. The six issues under the "Phase X: Rejected" milestone (rejected, never worked) are excluded throughout.

Review gate. The current month's count of REQUEST_CHANGES rounds is derived from the GitHub pull-request review API (one round per review; a PR rejected in two months counts in both); earlier months are historical constants mined before the review agent posted rounds as formal PR reviews. Merged-PR counts come from the GitHub API. Feb shows more rejected than merged because rejected PRs often merged in a later month or were superseded.

Spend telemetry. Per-issue Claude-invoking workflow steps, total workflow runs, Actions runner minutes (billed where the repository is billed, wall-clock run duration otherwise -- the tile says which), and retry/self-heal cycle count, derived from GitHub workflow-run history and attributed to an issue via its branch name (owner-endorsed direction from the 2026-08-09 cost post-mortem, #3696). This is the raw signal an anomaly-watching process reads to judge whether spend on an issue looks unusual — deliberately not a fixed cap. Runs whose branch carries no issue number (release-branch pushes, cron sweeps) roll up to an "unattributed" bucket rather than being dropped. Rendered from data/spend.json, refreshed by the "Retro Dashboard - Dump Spend Telemetry" workflow; if that dump has not landed, the section says so instead of disappearing (#3808).

Churn cost. Spend telemetry says what a run cost to run; churn cost says what the agent spent thinking, and how much of that was re-onboarding rather than producing change (owner decision 2026-08-14, #3776). One round is one executed claude-code-action step — initial implement, review-fix, acceptance-fix, self-heal, review or standalone session — attributed to an issue by branch name and numbered per issue in chronological order. Within a round, assistant turns before the first file-modifying tool use count as context re-establishment and the rest as change production; the round's token total is split pro rata by that turn ratio. Usage is reported once per step rather than per turn, so the split is an explicit approximation, and rounds whose logs yield no turn markers are counted in token totals but excluded from the split. Huddle and standalone-session rounds run on the release branch, so they carry no issue attribution; they are counted in the totals as unattributed rather than guessed at. Dollars appear only when a price sheet was configured at dump time — the rates are owner-supplied and never committed to the repository, which ships only a zeroed example. Rendered from data/churn.json, refreshed by the "Retro Dashboard - Dump Churn Cost" workflow; if that dump has not landed, the section says so instead of disappearing (#3808).
