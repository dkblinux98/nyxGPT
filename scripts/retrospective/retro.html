Acceptance-perspective classification. The 182 issues labeled Acceptance Failure (implementation defects found at stakeholder acceptance, before release) are classified by root cause: escaped defect — broken behavior in code that had passed review (a review miss); spec gap — the delivered work matched the issue but the requirement itself was wrong or incomplete (redesigns, consolidations, UX corrections); workflow miss — the agent pipeline itself failed (review gate, branch hygiene, submission workflows). Classification is keyword-heuristic over titles and bodies, hand-reviewed.

Product management failures. The 26 issues labeled Improvement are counted as a separate failure statistic: an Improvement filed during acceptance testing means the spec itself was incomplete — a product-management (planning) failure, distinct from an Acceptance Failure (implementation defect). Improvements never gate a feature's move to release.

Failure-issue model (since 2026-08-02). A unique acceptance failure becomes a new issue labeled Acceptance Failure, related to the original feature via a Related feature: #N body line and a blocking dependency; the original stays closed. A fix that later fails stakeholder re-test reopens the same failure issue rather than filing a new one — so failure-issue counts understate total failure rounds.

Sprints. Sprint buckets are the Project's real Sprint iterations, read from the snapshot committed by the "Retro Dashboard - Dump Project Fields" workflow (scripts/retrospective/data/project_fields.json) — each issue lands in the sprint it was actually assigned to on the board, and Module values come from the Project's Module field. If the snapshot is missing, the builder falls back to calendar weeks bucketed by creation date and title-inferred modules (the sprint-axis caption says which mode is active). The last-7-days section always uses title-inferred modules. Milestones are the repo's phase milestones, ordered. The six issues under the "Phase X: Rejected" milestone (rejected, never worked) are excluded throughout.

Review gate. The current month's count of REQUEST_CHANGES rounds is derived from the GitHub pull-request review API (one round per review; a PR rejected in two months counts in both); earlier months are historical constants mined before the review agent posted rounds as formal PR reviews. Merged-PR counts come from the GitHub API. Feb shows more rejected than merged because rejected PRs often merged in a later month or were superseded.

Spend telemetry. Per-issue Claude-invoking workflow steps, total workflow runs, billable Actions runner minutes, and retry/self-heal cycle count, derived from GitHub workflow-run history and attributed to an issue via its branch name (owner-endorsed direction from the 2026-08-09 cost post-mortem, #3696). This is the raw signal an anomaly-watching process reads to judge whether spend on an issue looks unusual — deliberately not a fixed cap. Runs whose branch carries no issue number (release-branch pushes, cron sweeps) roll up to an "unattributed" bucket rather than being dropped. Shown only when data/spend.json has been refreshed by the "Retro Dashboard - Dump Spend Telemetry" workflow.

Last 7 days. The 57 REQUEST_CHANGES reviews on nyxGPT PRs between 2026-08-02 and 2026-08-09, parsed from the pull-request reviews themselves (Critical / Medium / Minor findings sections).
